# 비상정지 버튼 — 지연과 CPU

## 왜 재는가

이 프로젝트에서 PWM 을 커널로 내린 논리는 이랬다.

```
요구사항  :  버튼을 누르면 즉시 정지해야 한다
      ↓
현재 구조 :  PWM 을 유저스페이스가 만든다
             커널이 버튼을 감지해도 멈출 대상이 경계 너머에 있다
      ↓
결론      :  멈출 대상도 커널에 있어야 한다
```

이 논리를 숫자로 만든다. 세 구간을 같은 조건에서 잰다.

| | 감지 | 정지 판단 | 상태 |
| --- | --- | --- | --- |
| **A** | 유저 (폴링) | 유저 | 측정 완료 |
| **B** | 커널 (IRQ) | 유저 | 예정 |
| **D** | 커널 (IRQ) | 커널 | 예정 |

**A 를 먼저 재는 이유**: 폴링으로 요구사항을 만족한다면 커널 모듈이 필요 없다.
재보지 않고 "폴링은 느리다" 고 단정하면 그게 "배우려고 만들었다" 가 된다.

## 하드웨어

```
택트 스위치   물리 9번(GND) ── 물리 11번(GPIO17)
LED          물리 13번(GPIO27) ── [저항] ── LED ── 물리 14번(GND)
```

외부 풀업 저항은 쓰지 않았다. BCM2711 은 핀마다 약 50kΩ 풀업을 내장하고 있고,
그 저항이 직렬로 끼어 있어 눌렀을 때 전류를 66µA 로 제한한다(쇼트가 아니다).

⚠️ GPIO17 의 기본 풀 상태는 **DOWN** 이다(라즈베리파이는 GPIO 0~8 이 기본 UP,
9~27 이 기본 DOWN). 전원이 나가면 초기화되므로 부팅할 때마다 켜야 한다.
`button_poll` 은 `raspi-gpio set 17 ip pu` 를 직접 호출한다 — sysfs 에는 풀을
설정하는 방법이 없기 때문이다. **커널 모듈(B)로 가면 `gpiod_set_config()` 로
모듈이 스스로 켜므로 이 문제가 사라진다.**

## 하드웨어 디바운싱을 쓰지 않은 이유

캐패시터로 채터링을 없앨 수 있지만, RC 는 신호 경로에 시간 상수를 심는다.

```
τ = R × C.  10kΩ + 100nF 이면 1ms
→ 재려는 "µs 단위 지연" 에 회로의 ms 가 섞여 들어간다
```

**지연을 측정하는 것이 목적이므로** 신호는 건드리지 않고 코드로 거른다.
일반 제품이라면 반대 선택이 맞다 — 인터럽트가 덜 뜨고 회로가 깔끔하다.

# A — 유저스페이스 폴링

## 방법

`tools/button_poll` 이 sysfs 로 GPIO17 을 읽고, 떨어지는 엣지에서 상태를 뒤집어
`/dev/servo0` 에 `pan off` 를 쓴다. LED 도 유저가 켠다. **pigpio 는 쓰지 않았다** —
비교 대상이라 섞이면 안 된다.

파일은 한 번만 열고 `pread()` 로 반복해 읽는다(매번 open/close 하면 불공정하게
느려진다). CPU 는 `getrusage(RUSAGE_SELF)` 로 이 프로세스 것만 잰다.

```bash
./tools/button_poll --interval 10ms --seconds 20
./tools/button_poll --interval 1ms  --seconds 20
./tools/button_poll --interval 100us --seconds 20
./tools/button_poll --busy --seconds 20
```

## 결과 (조건당 20초)

| 모드 | 요청 간격 | 실제 주기 | CPU (1코어) | CPU (4코어) | 루프 횟수 |
| --- | --- | --- | --- | --- | --- |
| sleep | 10ms | 10,075µs | 0.26% | 0.06% | 1,986 |
| sleep | 1ms | 1,084µs | 2.70% | 0.67% | 18,453 |
| sleep | 100µs | **171µs** | 11.03% | 2.76% | 117,004 |
| busy | — | **2.1µs** | **99.78%** | 24.95% | 9,343,394 |

sysfs 읽기 1회 비용: **2.1 ~ 3.8µs**

```
반응 속도        CPU (1코어)
10   ms          0.26%
 1   ms          2.70%
 0.2 ms         11.03%
 0.002 ms       99.78%
```

**속도를 10배 올릴 때마다 CPU 가 대략 10배.** 폴링은 지연을 CPU 로 산다.

## 발견 ① nanosleep 에는 바닥이 있다

부대비용이 약 **75µs 로 거의 고정**이다.

```
10ms  요청 →  10,075µs     오차 +75µs   (0.7%)
1ms   요청 →   1,084µs     오차 +84µs   (8.4%)
100µs 요청 →     171µs     오차 +71µs   (71%)
```

요청이 작아질수록 부대비용이 전부를 차지한다. **잠들면서 폴링하면 약 170µs 아래로
내려갈 수 없고**, 그 아래를 원하면 안 자야 한다 → CPU 100%.

## 발견 ② 쉬는 것이 공짜가 아니다

루프 한 바퀴당 CPU:

| 모드 | 루프당 CPU | 내역 |
| --- | --- | --- |
| sleep | 19 ~ 29µs | 읽기 2~4µs + **재우고 깨우기 15~27µs** |
| busy | 2.1µs | 읽기만 |

busy 모드의 루프당 비용(2.14µs)이 측정된 읽기 비용(2.06µs)과 거의 같다.
sleep 모드의 나머지는 전부 문맥 전환 비용이다.

## 발견 ③ 채터링이 보이지 않았다 — 단, 의심할 이유가 있다

2.1µs 주기(busy)에서도 8번 눌러 8번만 감지됐다. 두 가지 가능성이 있다.

```
① 스위치가 실제로 깨끗하다
② printf + fflush 가 가려줬다     ← 의심스러운 쪽
```

엣지를 감지하면 터미널로 출력하는데, SSH 를 거치므로 수 ms 가 걸릴 수 있다.
그 사이에는 폴링을 하지 않아 튀는 구간이 통째로 지나간다.
**B 단계의 커널 핸들러에는 출력이 없으므로 거기서 판명된다.**

## 재지 못한 것

**"버튼을 실제로 누른 시각"** 은 유저스페이스가 알 수 없다. 알 수 있으면 그게 이미
인터럽트다. 그래서 A 의 최악 지연은 "실제 폴링 주기" 로 볼 수밖에 없다.

→ B 에서 커널이 눌린 시각을 기록하면, 그것을 기준 시계로 삼아 **A 의 진짜 지연을
다시 잴 수 있다.** 그때 이 표를 갱신한다.

## A 단계 판정

```
요구사항이 "10ms 안에 정지" 라면 폴링으로 충분하다.
1ms 간격이면 최악 1.08ms, CPU 는 4코어 기준 0.67%.
```

**정직하게 말하면 이 요구사항에서는 커널 모듈이 없어도 된다.**
그래서 커널로 가는 근거는 "폴링이 느리다" 가 아니라 다음 셋이어야 한다.

```
① 지연과 CPU 의 맞교환을 없앤다
   171µs 를 얻으려면 11%, 2µs 를 얻으려면 100% 를 태워야 한다

② 카메라 추적이 이미 CPU 를 50% 쓰고 있다
   여기에 11% 를 더 얹으면 추적 성능이 떨어진다

③ 멈출 대상이 이미 커널에 있다
   유저를 거치는 것은 왕복일 뿐이다
```

①이 사실인지는 B 에서 잰다.

# B — 커널 IRQ + 유저 정지

## 방법

커널이 GPIO17 에 인터럽트를 걸고, `/dev/button0` 을 `read()` 하며 잠들어 있는
유저 프로세스를 깨운다. 정지 판단은 여전히 유저스페이스가 한다.

```
A (폴링)   유저: "왔어?" "왔어?" "왔어?"      CPU 를 계속 쓴다
B (대기)   유저: "오면 깨워줘" (잠듦)          CPU 0
```

`read()` 가 돌려주는 줄에 **커널이 인터럽트를 받은 시각**이 들어 있다.

```
press 3 ktime=123456789012
```

`ktime_get()` 은 `CLOCK_MONOTONIC` 이라 유저의 `clock_gettime(CLOCK_MONOTONIC)` 과
직접 뺄 수 있다. **A 에서 잴 수 없었던 "진짜 지연" 이 여기서 나온다.**

```bash
./tools/button_wait --seconds 30
```

## 결과 (30초, 버튼 14회)

| | 최소 | 평균 | 최대 | CPU (1코어) |
| --- | --- | --- | --- | --- |
| 커널 IRQ → 유저가 앎 | 32.5µs | **56.3µs** | 78.3µs | **0.010%** |

### A 와 나란히 놓으면

| 방식 | 지연 | CPU (1코어) |
| --- | --- | --- |
| A 폴링 10ms | 10,075µs | 0.26% |
| A 폴링 1ms | 1,084µs | 2.70% |
| A 폴링 100µs | 171µs | 11.03% |
| A 폴링 busy | 2.1µs | 99.78% |
| **B 커널 IRQ** | **56µs** | **0.010%** |

```
폴링으로 171µs 를 얻으려면   CPU 11%
인터럽트로  56µs 를 얻는데   CPU 0.01%
                              → 1100배 적게 쓰면서 3배 빠르다
```

**A 의 결론("폴링은 지연을 CPU 로 산다")이 여기서 증명됐다.** 인터럽트는 그 맞교환
자체를 없앤다 — 평소에는 아무 일도 하지 않고, 하드웨어가 CPU 를 깨우기 때문이다.

### 지연이 두 무리로 갈린다

```
33µs 대   [1][2][3][8][9][10]
75µs 대   [4][5][6][7][11][12][13]
```

깨어난 프로세스가 인터럽트를 처리한 CPU 에서 바로 도느냐, 다른 CPU 로 옮겨 가느냐의
차이로 보인다. 확인하지 않았다.

## 채터링 — A 에서 안 보이던 것이 B 에서 드러났다

첫 구현(시간 창 20ms)으로 재보니 **5~6번 눌렀는데 22번 감지**됐다.
커널이 센 인터럽트는 47회였다.

### 왜 시간 창으로는 못 막나

```
0ms    누름 (falling)        받아들임 ✓
1~3ms  튐                    20ms 안 → 버림 ✓
500ms  뗌 (falling 포함)     20ms 밖 → 받아들임 ✗
```

떼는 순간에도 접점이 튀면서 falling 엣지가 생긴다. 그런데 **사람이 얼마나 오래
쥐고 있을지 모르므로** 창을 아무리 키워도 못 막는다. 그리고 시계만 보면
"눌렀다 뗀 것" 과 "두 번 누른 것" 이 완전히 같은 모양이다.

```
㉠ 한 번 누르고 0.5초 뒤 뗌     0ms falling,  500ms falling
㉡ 0.5초 간격으로 두 번 누름    0ms falling,  500ms falling
```

### 처방 — 조건을 시간에서 핀 상태로

```
바꾸기 전   "마지막 누름에서 20ms 지났으면 받는다"       시계를 본다
바꾼 뒤     "핀이 HIGH 로 돌아간 걸 확인했으면 받는다"   핀을 본다
```

떼는 순간에도 튀므로 곧바로 읽으면 안 된다. 그래서 **엣지가 올 때마다 정착 타이머를
20ms 뒤로 밀고**, 타이머가 울렸다는 사실(= 그동안 엣지가 없었다)을 "안정됐다" 의
증거로 쓴다. **주기적으로 확인하는 폴링이 아니다.**

```
0.5초 누르고 있을 때 하는 일
  폴링 방식(30ms 마다 확인)    17번 읽음
  타이머 밀기 방식             엣지 7개 → 재설정 7번, 타이머 발화 2번
                               조용한 477ms 동안 0번
```

알림은 **첫 엣지에 곧바로** 한다. 안정될 때까지 기다렸다 알리면 지연이 20ms 가 되어
인터럽트를 쓴 의미가 사라진다.

```
알림      첫 엣지에 즉시     → 지연 56µs 유지
잠금해제   조용해진 뒤 확인   → 정확함
```

⚠️ 양쪽 엣지를 받아야 한다. 누름만 받으면 깔끔하게 떼었을 때 엣지가 하나도 안 와서
잠금이 영영 안 풀린다. (`IRQF_TRIGGER_BOTH` 라는 상수는 없다 —
`IRQF_TRIGGER_RISING | IRQF_TRIGGER_FALLING` 이 양쪽 엣지다.)

### 결과

```bash
cat /sys/class/servo/servo0/button
```
```
irq 68  accept 14  reject 54  armed 1  level 1
```

**누름 하나당 인터럽트가 약 5개 온다.** 1개만 받고 4개를 버린다. 14회 감지 = 누른 횟수.

### 여기서 배운 것

```
폴링      일정 간격으로 "찍어서" 본다  →  찍는 순간에 없으면 못 본다
인터럽트  하드웨어가 변화를 다 잡는다  →  µs 짜리 튐도 전부 온다
```

**A 가 깨끗했던 건 스위치가 좋아서가 아니라 폴링이 놓쳤기 때문이다.**
인터럽트로 얻은 것(지연 µs, CPU 0)에는 대가가 따른다 — 채터링을 직접 처리해야 한다.

# A 재측정 — 커널 기준시계로

## 왜 다시 재나

A 의 지연은 "폴링 주기와 같을 것" 이라는 **추정**이었다. B 를 만들면서 커널이 진짜
눌림 시각을 들고 있게 됐으므로, 그것을 기준시계로 삼아 같은 잣대로 다시 잰다.

```
지연 = 폴링이 알아챈 시각 − 커널이 인터럽트를 받은 시각
```

`/sys/class/servo/servo0/press` 가 `<번호> <ktime ns>` 를 돌려준다. 번호가 바뀌지
않았으면 커널이 튐으로 버린 것이므로 유저 쪽에서도 세지 않는다.

⚠️ **모듈이 GPIO17 을 쥐고 있어 `/sys/class/gpio` 로는 export 가 안 된다**(EBUSY).
커널이 핀 소유권을 인지한다는 것의 실제 결과다 — pigpio 는 `/dev/mem` 으로 우회하므로
이 충돌이 감지되지 않는다. 그래서 드라이버가 `level` 속성으로 값을 내주고, 폴링은
그것을 읽는다. 둘 다 파일 한 번 읽기이고 읽기 비용도 2.6~4.9µs 로 비슷하다.

```bash
./tools/button_poll --pin /sys/class/servo/servo0/level --interval 10ms --seconds 20
```

## 결과 (조건당 20초, 버튼 약 5회)

| 모드 | 실제 주기 | **진짜 지연 (최소/평균/최대)** | CPU (1코어) |
| --- | --- | --- | --- |
| sleep 10ms | 10,082µs | 134 / **5,018** / 8,571µs | 0.31% |
| sleep 1ms | 1,080µs | 2 / **542** / 1,019µs | 2.34% |
| busy | 2.5µs | −4.7 / **−2.9** / −1.1µs | 99.92% |

## 모형이 맞았다

예측은 "버튼은 주기 안 아무 때나 눌리므로 평균 지연은 주기의 절반" 이었다.

| 모드 | 주기의 절반 | 실측 평균 | 차이 |
| --- | --- | --- | --- |
| 10ms | 5,041µs | 5,018µs | −22µs |
| 1ms | 540µs | 542µs | +2µs |

**0.4% 오차 안으로 맞았다.** 10회씩밖에 안 쟀는데 이 정도면 모형이 옳다.

## 뜻밖의 발견 — 지연이 음수로 나왔다

busy 모드에서 **폴링이 커널보다 먼저 알아챘다.**

```
물리적 엣지
   ├─ 폴링이 핀을 읽음      엣지 + 0~2.5µs  (평균 1.2µs)
   └─ 인터럽트 → ISR 실행   엣지 + ?µs

실측 평균 −2.9µs = 1.2µs − ?  →  ISR 실행이 엣지로부터 약 4µs
```

**인터럽트가 하드웨어에서 핸들러까지 도달하는 데 약 4µs 걸린다.** 재려던 값이 아닌데
얻어걸렸다.

### 그래서 기준시계에 한계가 있다

```
우리가 "눌린 시각" 이라 부른 것  =  ISR 이 실행된 시각
진짜 물리적으로 눌린 시각        =  그보다 약 4µs 전
```

이 편향은 모든 측정에 똑같이 들어 있다.

```
A 10ms   5,018µs → 실제 약 5,022µs    영향 0.08%.  무시 가능
B IRQ       56µs → 실제 약    60µs    영향 7%.    적어둘 값
```

진짜 엣지 시각을 알려면 오실로스코프나 로직 애널라이저가 필요하다.

## 채터링이 드디어 보였다

busy 모드에서 **엣지 18회를 감지했는데 커널이 인정한 것은 10회**였다. 8회는 튐이다.

```
irq 121  accept 30  reject 91      (모듈 적재 이후 누적)
```

앞의 "발견 ③" 에서 A 가 깨끗해 보였던 것은 스위치가 좋아서가 아니었다.
**폴링은 자기가 무엇을 놓치는지, 무엇을 잘못 세는지 알 수 없다.** 비교할 기준이
생기고 나서야 보였다.

# 통합 결과

| 방식 | 지연 (평균) | CPU (1코어) | 채터링 |
| --- | --- | --- | --- |
| A 폴링 10ms | 5,018µs | 0.31% | 못 봄 |
| A 폴링 1ms | 542µs | 2.34% | 못 봄 |
| A 폴링 busy | **≈0µs** | **99.92%** | 못 봄 |
| **B 커널 IRQ** | **56µs** | **0.010%** | 걸러냄 |

```
① 폴링도 빠를 수 있다.  단 CPU 100% 를 태울 때만
② 인터럽트는 폴링 1ms 대비 10배 빠르면서 CPU 를 234배 적게 쓴다
③ 폴링은 자기가 무엇을 놓치는지 알 수 없다
```

**"인터럽트가 무조건 빠르다" 가 아니라 "같은 속도를 CPU 없이 얻는다" 가 맞는 문장이다.**
