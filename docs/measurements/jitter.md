# hrtimer 타이머 지터

## 무엇을 재는가

서보의 각도는 펄스폭이 결정하고, 펄스폭은 hrtimer 콜백이 불린 시각 그 자체다.
콜백이 예정보다 늦으면 그만큼 펄스가 길어진다.

```
목표:   ┌──────────────┐
        0           1500us
실제:   ┌────────────────┐
        0             1520us    <- 콜백이 20us 늦음 = 펄스가 20us 길어짐
```

모듈이 매 콜백마다 `hrtimer_cb_get_time() - hrtimer_get_expires()` 를 재서
평균·최대·구간별 개수를 누적하고 sysfs 로 노출한다.

```
1도 = 2000us / 180도 = 11.1us
합격선 = deadzone 0.12 = 화면 +-19px = 약 3도 = 약 33us
```

**한계**: 재는 것은 "콜백이 예정대로 불렸는가"(스케줄링)이지 핀 전압이 실제로
뒤집힌 시각이 아니다. 진짜 파형을 보려면 오실로스코프가 필요하다.
같은 이유로 **pigpio 의 지터는 재지 못했다** — 우리 코드 밖이라 접근할 수 없다.
"DMA 라 더 좋을 것" 은 구조적 추론이지 측정이 아니다.

## 결과

표본 수 = 경과초 x 100 (2채널 x 50Hz x 2회).

| 조건 | pan 평균 | pan 최대 | 3도 초과 |
| --- | --- | --- | --- |
| 유휴 | 4.2us (0.4도) | 25.9us (2.4도) | 0% |
| **4코어 풀부하** (`yes` x4) | **1.4us** | **23.9us** | **0%** |
| camtracker 부하 | 9.4us (0.9도) | 122.6us (11도) | 1.84% |
| camtracker + governor=performance | 9.3us | 110.1us | 1.91% |
| camtracker + taskset CPU3 | 9.7us | 98.2us | 2.30% |

가장 무거운 부하(4코어 100%)에서 지터가 **가장 작았다.** 부하량이 원인이 아니다.

### 히스토그램 (camtracker 부하, 표본 8570)

```
pan    <11us (<1도)    6429   75.0%
      <33us (1~3도)    1960   22.8%
      <55us (3~5도)     158    1.8%
     <110us (5~10도)     22    0.2%
     >=110us (10도+)      1    0.0%
```

평균·최대만으로는 "122us 가 한 번인지 백 번인지" 를 알 수 없어 구간별 개수를 넣었다.

### 눈으로 확인

4코어 풀부하 상태에서 서보를 60초간 관찰 — **미동 없음.**

## 원인 추적 — 가설 6개를 배제했다

| # | 가설 | 검증 | 결과 |
| --- | --- | --- | --- |
| 1 | 타이머 2개가 서로 늦춘다 | tilt 끄고 pan 만 측정 | 9.4 -> 9.3, 변화 없음 |
| 2 | CPU 절전 진입/복귀 지연 | `/sys/.../cpuidle` 확인 | 이 Pi 에 cpuidle 자체가 없음 |
| 3 | CPU 주파수 스케일링 | governor=performance (1800MHz 고정) | 9.4 -> 9.3, 변화 없음 |
| 4 | 채널(pan/tilt) 차이 | 여러 번 반복 | 실행마다 나쁜 쪽이 바뀜 |
| 5 | 단순 CPU 부하량 | `yes` x4 로 4코어 100% | 오히려 가장 좋음 (1.4us) |
| 6 | CPU0 의 카메라 인터럽트 경합 | `taskset -c 3` 으로 타이머를 CPU3 에서 시작 | 9.3 -> 9.7, 변화 없음 |

가설 6의 근거였던 것:

```
  43:  76072  0  0  0   unicam_capture0      <- 카메라 인터럽트가 전부 CPU0
  35:  89312  0  0  0   VCHIQ doorbell
```

CPU0 에 몰려 있는데도 CPU3 로 옮기는 게 효과가 없었다.

## 남은 후보 — 메모리 대역폭 / 캐시 오염

`yes` 와 `camtracker` 의 차이는 CPU 사용량이 아니라 **메모리를 얼마나 휘젓느냐** 다.

```
yes          L1 캐시 안에서만 돈다. 메모리를 거의 안 건드림   -> 1.4us
camtracker   카메라 DMA 1280x720 + DNN 추론으로 버스를 채움  -> 9.4us
```

인터럽트 핸들러도 메모리에서 코드와 데이터를 읽어야 하고, DNN 추론이 캐시를
밀어낸다. **소프트웨어로 고칠 수 없다.**

## 처음 판단 — 그리고 이 판단은 틀렸다

```
평균은 두 조건 다 1도 미만        -> 추적 품질에 영향 없음
최악 조건에서 눈으로 떨림 없음     -> 실사용 영향 없음
camtracker 부하에서 2% 가 3도 초과 -> 간헐적 움찔거림에 기여 가능
```

이렇게 보고 **고치지 않기로 했다.** 2026-09-27 03:25 에 눈으로 뒤집혔다.

### 뒤집힌 과정 — pigpio 와 나란히 비교

"추적 흔들림이 며칠 전보다 심하다" 는 관찰에서 시작했다. 9/22 에는 pigpio 였고
지금은 커널 드라이버다. **설정을 전부 같게 두고 펄스 생성 주체만 바꿔** 연달아 돌렸다.

```
같은 것   max_step 4.0, deadzone 0.12, 같은 모델·카메라, 연속 실행
다른 것   펄스를 만드는 주체 (pigpio DMA  vs  커널 hrtimer)
```

**pigpio 쪽이 확실히 덜 흔들렸다.**

### 왜 평균이 속였나

```
평균  9.4us  = 0.9도      <- 이것만 보고 "영향 없다" 고 판단했다
최대 122us   = 11도
3도 초과      1.84%        <- 초당 100 펄스 중 약 2번
```

서보는 펄스 하나하나에 반응한다. 1.84% 면 **초당 두 번씩 몇 도가 튄다**는 뜻이고,
사람 눈은 평균이 아니라 그 두 번을 본다.

두 가지를 잘못했다.

```
① 히스토그램까지 만들어 놓고 해석을 평균으로 했다
   분포를 재는 것과 분포로 판단하는 것은 다른 일이다

② "60초간 눈으로 확인" 을 4코어 풀부하에서 했다
   그 조건은 지터가 가장 작았던 조건이다.  정작 문제가 되는
   camtracker 부하에서는 눈으로 보지 않았다
```

### 고쳐 쓴 결론

```
지터는 실사용에 영향을 준다.  근본 해결은 하드웨어 PWM 이다.
```

체감 흔들림에는 KCF 트래커 드리프트(프레임의 12%가 10px 이상, 약 3도)도 함께
기여한다. 어느 쪽이 얼마나 기여하는지는 **하드웨어 PWM 으로 지터를 없앤 뒤 남는
흔들림**으로 가른다. → [tracking.md](tracking.md)

## 근본 해결책과, 그것을 쓰지 않은 이유

GPIO12/13 은 BCM2711 의 하드웨어 PWM 핀(PWM0_0/PWM0_1)이다. `CONFIG_PWM_BCM2835=m`,
`/boot/overlays/pwm-2chan.dtbo` 가 준비돼 있어 전환할 수 있었고, 그러면 칩이 파형을
만들어 지터가 사라진다.

쓰지 않은 이유는 커널 헤더에 있다.

```c
static inline void pwm_disable(struct pwm_device *pwm) { might_sleep(); ... }
```

`pwm_enable` / `pwm_disable` / `pwm_apply_state` 전부 `might_sleep()` 이다.
**잠들 수 있는 함수는 인터럽트 핸들러에서 부를 수 없다.**

| | 지터 | IRQ 에서 즉시 정지 | 쓸 수 있는 핀 |
| --- | --- | --- | --- |
| hrtimer (이 드라이버) | 부하 시 나빠짐 | 가능 (`gpiod_set_value`) | 아무 GPIO |
| 하드웨어 PWM | 최상 | 불가 (workqueue 경유) | GPIO12/13 고정 + DT 오버레이 |

이 프로젝트의 요구사항은 "버튼을 누르면 즉시 정지" 다. 그 축에서는 hrtimer 가 맞다.
**어느 쪽이 무조건 낫지 않고, 요구사항이 선택을 결정한다.**
