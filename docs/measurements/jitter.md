# hrtimer 타이머 지터

## 무엇을 재는가

서보의 각도는 펄스폭이 결정하고, 펄스폭은 hrtimer 콜백이 불린 시각 그 자체다.
콜백이 예정보다 늦으면 그만큼 펄스가 길어진다.

```
목표:   ┌──────────────┐
        0           1500us
실제:   ┌────────────────┐
        0             1520us    <- 콜백이 20us 늦음 = 펄스가 20us 길어짐
```

모듈이 매 콜백마다 `hrtimer_cb_get_time() - hrtimer_get_expires()` 를 재서
평균·최대·구간별 개수를 누적하고 sysfs 로 노출한다.

```
1도 = 2000us / 180도 = 11.1us
합격선 = deadzone 0.12 = 화면 +-19px = 약 3도 = 약 33us
```

**한계**: 재는 것은 "콜백이 예정대로 불렸는가"(스케줄링)이지 핀 전압이 실제로
뒤집힌 시각이 아니다. 진짜 파형을 보려면 오실로스코프가 필요하다.
같은 이유로 **pigpio 의 지터는 재지 못했다** — 우리 코드 밖이라 접근할 수 없다.
"DMA 라 더 좋을 것" 은 구조적 추론이지 측정이 아니다.

## 남은 후보 — 메모리 대역폭 / 캐시 오염

`yes` 와 `camtracker` 의 차이는 CPU 사용량이 아니라 **메모리를 얼마나 휘젓느냐** 다.

```
yes          L1 캐시 안에서만 돈다. 메모리를 거의 안 건드림   -> 1.4us
camtracker   카메라 DMA 1280x720 + DNN 추론으로 버스를 채움  -> 9.4us
```

인터럽트 핸들러도 메모리에서 코드와 데이터를 읽어야 하고, DNN 추론이 캐시를
밀어낸다. **소프트웨어로 고칠 수 없다.**

### 왜 평균이 속였나

```
평균  9.4us  = 0.9도      <- 이것만 보고 "영향 없다" 고 판단했다
최대 122us   = 11도
3도 초과      1.84%        <- 초당 100 펄스 중 약 2번
```

서보는 펄스 하나하나에 반응한다. 1.84% 면 **초당 두 번씩 몇 도가 튄다**는 뜻이고,
사람 눈은 평균이 아니라 그 두 번을 본다.

```
② "60초간 눈으로 확인" 을 4코어 풀부하에서 했다
```

## 하드웨어 PWM 으로 검증 (2026-09-27 04:10~04:50)

`dtoverlay=pwm-2chan,pin=12,func=4,pin2=13,func2=4` 를 올려 GPIO12/13 을 칩의 PWM
회로에 붙였다. 온보드 아날로그 오디오가 같은 PWM 채널 두 개를 쓰므로
`dtparam=audio=on` 은 껐다(HDMI 오디오는 다른 경로라 영향 없음). 재부팅이 필요하다.

두 단계로 확인했다. 먼저 명령을 고정해 지터만 분리하고, 그다음 실제 추적을 했다.

### ① 고정 유지 — 명령을 고정해 두고 부하만 건다

체감 흔들림에는 원인이 셋 섞여 있다.

```
① PWM 지터        CPU 가 바쁘면 펄스 길이가 틀어진다
② 검출 박스 잡음   사람이 가만히 있어도 박스 중심이 튄다
③ 트래커 드리프트  KCF 가 프레임의 10%대에서 밀린다
```

①만 보려면 명령이 변하지 않아야 한다. **명령이 고정인데 서보가 움직이면 그것은
펄스가 틀어진 것 말고 설명이 없다.** ②③은 명령을 통해서만 서보에 닿기 때문이다.

```
부하    camtracker --no-track  (카메라 + 검출 + 인코딩 + RTSP 송출, 모터는 dummy)
        CPU 55.2%,  "타겟 있음"(KCF 보간까지 동작),  3.5~7.2 fps
서보    sysfs 로 1500us 고정.  30초간 한 번도 바꾸지 않음
결과    미동 없음
```

새벽에 한 "4코어 풀부하에서 60초 관찰" 이 왜 무의미했는지가 여기서 갈린다.
지터가 문제가 되는 조건은 `yes` x4 가 아니라 camtracker 부하다(전자는 1.4us,
후자는 9.4us). **이번에는 문제가 나타나는 조건에서 봤다.**

### 남은 흔들림 — 처음 해석은 틀렸다

처음에 이렇게 적었다.

```
DET 중심 이동 평균 30.7px ÷ 6.4px/도 = 약 4.8도의 가짜 오차
-> max_step 4.0 에 걸려 서보가 4도씩 움직인다
```

30분 뒤 모델 비교([model.md](model.md))를 하다가 틀렸음을 알았다. **DET 샘플의 간격이
1초**라, 그 사이에 사람이 실제로 걸어간 거리가 전부 "박스 이동" 으로 잡힌 것이다.

```
04:49:44 -> 45   115.4px    걸어가는 중
04:49:45 -> 46    65.1px    걸어가는 중
04:49:40 -> 41     1.1px    정지 구간
04:49:48 -> 49     0.0px    정지 구간

전체 평균  30.7px        정지 구간 평균  0.5px (최대 1.1px)
```

정지한 사람을 93프레임 찍어 오프라인으로 다시 재도 같은 값이 나왔다(0.3px).
**검출 박스는 사람이 정지하면 0.5px = 0.08도로 거의 완벽하다.**

평균 하나로 판단해서 틀린 것이 이 문서에서 **두 번째**다. 처음은 지터 평균 9.4us,
이번은 DET 이동 평균 30.7px 이었다. 평균을 쓰기 전에 **그 안에 다른 조건이 섞여
있는지 먼저 갈라야 한다.** 이번 것은 "정지"와 "보행"이 한 평균에 들어 있었다.

### 그래서 지금 상태

```
정지 중   검출 0.5px + 지터 0    ->  명령 변화 0.0도.  서보가 완전히 멈춘다 (눈으로 확인)
이동 중   명령 변화 최대 4.00도  =   max_step 포화
```

이동 중에 남은 흔들림의 원인은 검출 잡음이 아니라 셋이다.

| 원인 | 성격 | 수단 |
| --- | --- | --- |
| max_step 4.0 포화 | 1틱당 이동 상한. 제어 주기 5fps 라 초당 20도가 한계 | max_step·Kp 조정 — 오버슈트와 맞바꾼다 |
| 검출 지연 약 220ms | 정보가 늦게 온다. 제어기로는 못 고친다 | 지연 보상(구현됨), 예측 개선, 검출 가속 |
| KCF 드리프트 | 보간 프레임이 밀린다. 10px 이상이 16% | redetect_interval 축소, 트래커 교체 |

### syspwm 의 한계 — 비상정지가 없다

커널 모듈이 그림에서 빠지므로 버튼 IRQ 를 받을 주체가 없다.

```
kservo   camtracker -> /dev/servo0 -> servo.c (hrtimer 로 핀을 흔든다 + 버튼 IRQ)
syspwm   camtracker -> /sys/class/pwm -> bcm2835-pwm -> 칩 회로   (servo.c 없음)
```

흔들림을 재기 위한 실험용 백엔드다. 비상정지는 커널 모듈을 PWM 소비자로 개조해
되찾는다(아래).

## hrtimer 를 먼저 택한 이유

GPIO12/13 은 BCM2711 의 하드웨어 PWM 핀(PWM0_0/PWM0_1)이다. `CONFIG_PWM_BCM2835=m`,
`/boot/overlays/pwm-2chan.dtbo` 가 준비돼 있어 전환할 수 있었고, 그러면 칩이 파형을
만들어 지터가 사라진다.

처음에 쓰지 않은 이유는 커널 헤더에 있다.

```c
static inline void pwm_disable(struct pwm_device *pwm) { might_sleep(); ... }
```

`pwm_enable` / `pwm_disable` / `pwm_apply_state` 전부 `might_sleep()` 이다.
**잠들 수 있는 함수는 인터럽트 핸들러에서 부를 수 없다.**

| | 지터 | IRQ 에서 즉시 정지 | 쓸 수 있는 핀 |
| --- | --- | --- | --- |
| hrtimer (이 드라이버) | 부하 시 나빠짐 | 가능 (`gpiod_set_value`) | 아무 GPIO |
| 하드웨어 PWM | 최상 | 불가 (workqueue 경유) | GPIO12/13 고정 + DT 오버레이 |

이 프로젝트의 간판 요구사항은 "버튼을 누르면 즉시 정지" 였다. 그 축에서는 hrtimer 가
맞다. `gpiod_set_value()` 는 IRQ 핸들러에서 그냥 불린다. 핀 자유도도 hrtimer 쪽이
넓다 — `insmod` 한 줄로 아무 GPIO 에나 붙는다. 하드웨어 PWM 은 `config.txt` 수정,
재부팅, 오디오 끄기를 요구했고 그 비용은 실재했다(2026-09-27 오전에 그대로 겪었다).

**어느 쪽이 무조건 낫지 않고, 요구사항이 선택을 결정한다.** 틀린 것은 이 문장이
아니라 요구사항 목록이었다 — **"부하 중에도 떨리지 않는다" 가 빠져 있었다.**

### 다음 단계 — 커널 모듈을 PWM 소비자로 개조

`syspwm` 은 흔들림을 잡았지만 비상정지를 잃었다. 둘을 함께 가지려면 `servo.c` 가
hrtimer 로 핀을 흔드는 부분만 칩에 넘기고, 캐릭터 디바이스·대기 큐·sysfs·버튼 IRQ
는 그대로 두면 된다. 사용자 입장의 `/dev/servo0` 인터페이스는 바뀌지 않는다.

| | 지터 | 비상정지 | 핀 자유도 |
| --- | --- | --- | --- |
| hrtimer (현재 kservo) | 부하 시 최대 11도 | O 1.6us | O 아무 GPIO |
| 하드웨어 PWM (syspwm) | 없음 | X | X GPIO12/13 |
| **개조 후** | 없음 | O (아래 방법) | X GPIO12/13 |

풀어야 할 것이 둘 있다. "hrtimer 부분만 지우면 끝" 이 아니다.

```
① 비상정지    pwm_disable() 은 might_sleep() 이라 IRQ 핸들러에서 못 부른다.
              핀 기능을 PWM(ALT0) -> GPIO 출력으로 되돌려 LOW 로 떨어뜨린다.
              레지스터 한 번 쓰기라 잠들지 않는다.  (메트로놈은 울지만 선을 뽑는 셈)

② 채널 확보    커널 안의 PWM 소비자는 보통 디바이스 트리에 "이 채널을 쓴다" 가
              적혀 있어야 pwm_get() 을 할 수 있다. insmod 로 올리는 모듈에는 그
              노드가 없다.  후보: pwm_add_table() 로 연결표를 코드에서 등록,
              또는 모듈용 DT 오버레이 작성.
```
