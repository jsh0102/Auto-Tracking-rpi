# 실제 추적 로그 분석

커널 드라이버(`backend: kservo`)로 사람을 추적한 40초간의 기록.
원본: `tracking_kservo.log` (290줄)

재현: `SECS=40 ./scripts/tune_capture.sh <출력경로>`

## 동작 확인

```
motor: 커널 드라이버 사용 (/dev/servo0)
app: 시작: detect=ssd motor=kservo rtsp=disabled
```

전송 실패 경고 0건 — 커널이 모든 명령을 받아들였다.

## 제어 통계 (pan 축, 145회)

| 항목 | 값 |
| --- | --- |
| 명령 없음 (데드존 안) | 114회 (79%) |
| 명령 있음 | 31회, 평균 4.2도 |
| `max_step`(6.0도) 포화 | 8회 = 명령의 26% |

명령의 1/4이 한 번에 움직일 수 있는 최대치에 붙어 있다. **추적이 거칠게 느껴지는
직접적인 원인이다.**

## 오차 분포

```
|err| < 0.12 (데드존)   112회  77%
0.12 ~ 0.25              23회  16%
0.25 이상                10회   7%
```

## 흔들림의 원인 — KCF 트래커 드리프트

검출 보간용 KCF 트래커의 박스가 한 프레임에 크게 튄 경우:

```
117회 중 14회 (12%), 평균 20px
20px / 6.4px/도 = 약 3도
```

전형적인 구간:

```
21:47:51  trk 이동=(-13)     박스가 왼쪽으로 밀림
21:47:51  trk 이동=(-11)     -> err -0.18, 데드존 넘음 -> 서보 -3.0도
21:47:51  trk 이동=(+29)     <- 재검출이 제자리로 당김
```

사람은 가만히 있었는데 **박스가 혼자 움직였다.**

## 튜닝 후보 (미적용)

| 값 | 현재 | 제안 | 효과 |
| --- | --- | --- | --- |
| `track.pan_pid.max_step` | 6.0 | 4.0 | 최고 속도 1/3 감소. 부드러워짐 |
| `track.deadzone` | 0.12 | 0.15 | +-24px 까지 무시. 잔떨림 흡수 |
| `detect.redetect_interval` | 5 | 3 | KCF 드리프트를 더 자주 교정 (CPU 증가) |

적용하지 않은 이유: 드라이버 작업이 우선이었고, 튜닝은 되돌리기 쉬운 값 변경이라
나중에 해도 된다.

## 지터와의 비교

| 원인 | 빈도 | 크기 | 지속 |
| --- | --- | --- | --- |
| KCF 드리프트 | 프레임의 12% | 약 3도 | 여러 프레임 |
| 타이머 지터 | 펄스의 2% | 3~5도 | 단발 (20ms) |

**체감 흔들림의 주범은 KCF 다.** 지터를 0으로 만들어도 대부분 남는다.
→ [jitter.md](jitter.md)

# tilt 가 한 번에 20도 튀는 현상 (2026-09-28)

하드웨어 PWM 으로 바꾼 뒤 실제 추적을 돌리다 발견했다. **원인은 제어기도 서보도
아니고 검출 입력이다.**

## 증상

```
좌우로만 움직였는데 카메라가 위아래로 크게 돌아간다
2초 만에 20도가 몰아치고, 되돌아오지 않는다
3초 뒤 "타겟 소실 — 홈 복귀" 로 원위치
```

## 틱 단위 기록

```
시각        박스y   y오차   이번틱   tilt
21:24:33     120   +0.00   +0.0   -29.2    평온
21:24:33     166   -0.38   -4.0   -29.2    박스가 무너진 순간
21:24:34     166   -0.31   -4.0   -33.2
21:24:35     188   -0.57   -4.0   -37.8
21:24:35     188   -0.38   -4.0   -41.8
21:24:35     184   -0.22   -1.5   -45.8
21:24:38     120   +0.00   +0.0   -49.7    다시 조용. 기운 채로 고정
```

연속 6틱이 전부 `max_step`(4도) 최대치로 나갔다. 제어 루프가 초당 5회이므로
**약 2초에 20도**, 눈에는 한 번에 확 움직이는 것으로 보인다.

## 원인 — 사람이 프레임보다 크다

검출 박스 115개 중 대부분이 `y=0` 에서 시작해 `y=239` 에서 끝났다. 위아래가 화면
경계에 붙어 있다는 뜻이다.

```
박스가 위아래로 잘리면  ->  중심 y = (0+239)/2 = 120  ->  항상 화면 정중앙
                           카메라가 어디를 향하든 같은 값이 나온다
```

**값이 항상 같으면 그것은 측정이 아니다.** `err_y = 0.01` 은 "완벽히 맞췄다" 가
아니라 "세로로는 아무 정보가 없다" 였다. 제어기가 세로로 눈이 먼 상태였던 것이다.

여기에 간헐적인 부분 검출이 겹친다.

```
정상      높이 239 (프레임에 잘림)       중심 120  ->  오차 0  ->  가만히
부분검출  높이 54~136 (하반신만)         중심 189  ->  오차 -0.57  ->  확 움직인다
직후      다시 잘린 박스                 중심 120  ->  오차 0  ->  움직인 자리에 고정
```

제어기는 증분식(`moveBy`)이라 **오차 0 은 "중앙으로 돌아가라" 가 아니라 "지금 각도를
유지하라" 다.** 잘못 움직여도 되돌릴 신호가 생기지 않는다.

### 심한 붕괴는 움직일 때만 일어났다

|  | 정상(높이≥180) | 약간 작음 | 심하게 무너짐(<120) |
| --- | --- | --- | --- |
| 정지 중 | 47 | 1 | 0 |
| 움직이는 중 | 43 | 0 | 3 |

모션 블러로 검출이 몸의 일부만 잡는 것으로 보인다. **좌우로만 움직여도 세로가
흔들린 이유**가 이것이다 — 박스가 무너질 때 가로 중심은 거의 그대로지만 세로
중심은 통째로 이동한다.

## 확인한 것과 배제한 것

```
tilt_invert 설정    정상.  펄스 1200=위 / 1800=아래, tracker 의 "위로"=낮은 펄스  ✅
제어기 이득·데드존   무관.  오차가 진짜였다면 맞는 동작이었다
서보·PWM            무관.  명령대로 움직였다
```

## 고치는 방법과, 고치지 않기로 한 이유

```
A  거리를 벌린다 / 화각을 넓힌다     사람이 프레임에 들어오면 중심이 다시 정보가 된다
B  잘린 방향은 제어에 쓰지 않는다     "박스가 경계에 닿았으면 그 축의 오차를 믿지 않는다"
C  높이 급변 프레임을 버린다          ✗ 앉는 동작을 막는다. 앉으면 실제로 키가 절반이 된다
```

B 를 구현하려다 멈췄다. **경계에 닿는 경우만 덮고, 근거리에서 좌표 자체가 흔들리는
것은 그대로 남기 때문이다.** 절반짜리 처방에 코드를 늘리는 대신 원인을 기록해 둔다.

근본은 A(거리·화각) 또는 검출 개선이다. → [model.md](model.md)
